# Production promotion

## Current candidate status

The accepted interface and the experimentally qualified stop/finalize correction
are integrated in the candidate. The missing-evidence closure blocker is resolved
locally. Production promotion is not approved by this document.

Previously, verifying an unavailable stored object interrupted closure before
the stopped-capture receipt was admitted. Chronicle now distinguishes confirmed
browser shutdown and recorder drain from stored-content availability. A typed
artifact-read failure records incomplete capture; only explicit failure sealing
may finish with unavailable evidence. Native reservation recovery likewise
returns no recovered recording when its authenticated events are unavailable.
Neither path invents receipts, recaptures the application or bypasses ownership.
Recorder-drain, database, receipt-shape and ownership failures still propagate.

The isolated experiment preserved the failing pre-stop missing/tampered cases
before the correction. The adopted Chronicle suite passes 105 tests, including
18 dedicated stop/finalize cases. The real Chrome/database closure matrix passes
18 tests on repeated execution, including lost stop/seal acknowledgments,
unconfirmed-stop refusal and no-browser recovery. Fast qualification and
production-only dependency qualification pass.

The final production-image API/MCP/worker journey also passes the original
active-capture missing-file scenario, refuses successful run finalization,
publishes a limited application report with an inconclusive check and incomplete
coverage, and exercises authenticated desktop/mobile evidence views. The older
verifiers' blanket report-refusal assertions were corrected to the established
limited-report contract; successful evidence and run requirements were not
weakened. Restoring the missing file does not rewrite the admitted failure seal.

This is local candidate evidence, not required CI for a release commit, a new
ten-app blind cohort, or authorization to activate an adapter, merge or deploy.
Complete the remaining account-dialog keyboard review and promotion sequence
below. Public identity-provider configuration is a deployment step, not an
unresolved application defect.

## Accepted interface

The product interface uses the accepted cool-black composition, restrained lime
accents, clear work-state icons and readable hierarchy across Missions, journey
attempts, Reports, the dashboard and workspace settings. The public home keeps
the original identity and headline, with the accepted report illustration and
workflow layout.

The public presentation invokes Scry's existing account lifecycle. It does not
contain a second authentication implementation. Preview controls, fictional
workspace adapters, comparison links and disconnected account dialogs are not
part of the shipped application. Public example reports remain explicitly
fictional; they are not customer test results.

A Mission is the starting point for the user's testing objective. Its journeys,
attempts and evidence remain linked to the compiled application report. Report
navigation stays visible and identifies the section currently being reviewed.
Application observations and testing progress remain distinct. Operator execution
diagnostics must not become customer application findings.

## Candidate acceptance

Before preparing a release:

- Run `pnpm qualify fast` for formatting, types, source closure, component
  regressions, the web build, publication rules and deployment-controller checks.
- Run `pnpm qualify production-dependencies` and `pnpm qualify deployment`.
- Run `pnpm qualify deployed-smoke` on the complete current source, not only the
  isolated design preview. Review its authenticated dashboard and native evidence.
- Keep required database, worker and owner qualifications attached to the exact
  release commit through the existing required-qualification workflow. A local
  component invocation can explicitly skip environment-dependent cases; those
  skips are not integration passes.
- Run `pnpm test:auth-activity` for the optional deployed Supabase activity caller.
- Review real sign-in/sign-up entry points, narrow-screen navigation, mission
  selection, application checks, report section tracking and evidence retrieval.
- Verify that Docker excludes both TypeScript and TSX test files. Test-only helpers
  must not be required to build the production web application.

The interface adoption itself changes neither browser execution authority nor
evidence custody, storage policy or database schema. The separately qualified
stop/finalize correction changes artifact-failure handling at closure without
changing authority or schema. Neither change converts earlier ten-app
assessments into ten new blind runs on a single final binary. Their recovery,
coverage and unresolved-attribution limits remain in the controlled-integration
record.

## Promotion sequence

1. Review the complete candidate diff, including the reporting, authentication,
   branding and other existing work accompanying this interface adoption. Preserve
   unrelated changes; do not promote a subset that breaks their compatibility.
2. Commit the reviewed candidate and obtain required CI results for that exact
   commit. A dirty worktree, a local build or a different commit's results are not
   a qualified release.
3. Confirm the intended public origin, Supabase callback/return allowlist, Google
   consent configuration and any email delivery settings. The retained local
   Google setup is External / Testing for the owner; this alone does not establish
   public-customer login readiness. Do not publish consent or expand provider
   access implicitly.
4. Publish through the existing qualified-image workflow. Preserve its exact
   release identity, immutable image reference and publication receipt.
5. Rehearse the published image in staging with the intended runtime configuration.
   Verify authentication, an application journey, screenshots/recording retrieval,
   the compiled report and operational health.
6. For a production-tier promotion, verify configured backups, restore evidence,
   monitoring, alert delivery and deployment admission. A default staging preflight
   does not prove production settings exist or that a live restore succeeds.
7. Obtain promotion approval, then deploy the exact qualified image through the
   existing deployment controller. Retain its health and rollback receipt.

## Rollback and limits

Keep the previous qualified image and configuration available. Use the existing
deployment controller's rollback process if post-promotion health or workflow
checks fail; do not substitute source edits on the server. This presentation-only
adoption and stop/finalize correction require no schema rollback and rewrite no
historical reports or media.

Local candidate qualification does not establish live TLS, DNS, production
credentials, email delivery, all-browser support, mobile-browser execution,
universal app compatibility or perfect masking. These limits must remain explicit
in the promotion decision rather than being hidden by a UI-only acceptance.
