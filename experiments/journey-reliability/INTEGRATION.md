## Capacity decision and qualification history

### Live-session capacity

The two-browser memory kill is an operational failure with an unenforced lifecycle
invariant: startup/command job concurrency ends before the browser lifetime ends.
The native engine retains live sessions between jobs, so lowering BullMQ job
concurrency alone does not bound total browser memory. This differs from an app
interaction defect and does not justify replacing Playwright.

Options before implementation:

- More worker memory / sequential lab operation: reversible containment and useful
  for completing app acceptance, but no enforceable upper bound on live sessions.
- Configurable lifetime admission: recommended bounded subsystem correction. One
  authoritative admission rule must cover both session creation paths, exact
  retries, startup, closure, cancellation and crash recovery. Capacity refusal must
  occur before excess launch and explain that no business action ran. Existing
  commands and finalization must not be blocked by startup capacity. No app-name
  budgets or automatic replay. Concurrent admission and stale/recovered closure
  require real database/runtime tests before activation.
- A distributed scheduling/fleet rebuild: broader migration, ownership/routing and
  operational work than this observed failure currently justifies.

Primary-source comparison: [BullMQ job concurrency](https://docs.bullmq.io/guide/workers/concurrency)
limits jobs being processed; [Browserless session capacity](https://docs.browserless.io/enterprise/private-deployment/worker-settings)
limits concurrent browser sessions to avoid resource exhaustion. These support the
distinction, not a claim that Scry has already implemented their scheduling model.
The user approved the bounded correction. Both creation paths now use one short
transactional admission function; active Session rows remain the durable
reservation through existing closure. The default is one live Session per
database; queue-job concurrency is unchanged. Exact replay precedes capacity
refusal. An additive partial index avoids scanning historical attempts. Deployment
replicas must share configuration, and rollout must drain old writers: an old
binary does not implement the new admission invariant. Existing over-limit rows
are retained and must be finalized honestly, not silently deleted or expired.

Before/after relational characterizations failed on the previous implementation
and passed on the candidate, including competing entry paths, simultaneous exact
retries, creation rollback, terminal-label non-release and stale-owner recovery.
The coherent candidate image `90b103c22a1d` passed the actual public MCP/API/worker
crash experiment: excess start refused while the owned browser stayed usable;
after a confirmed worker kill/restart and the full old lease interval, capacity

attempt. The separate actual production-image rerun also passed, as recorded
above; it does not replace the real-app assessments.

The one-browser-owning-worker topology is the qualified baseline. This admission
rule is not a distributed routing or worker-fleet scheduler. Raising the default
