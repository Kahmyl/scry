# Browser foundation experiment: evidence and decision

## Decision and scope

Use the official Playwright MCP adapter as the browser-control foundation, with Scry owning authorization, serialized durable action receipts, lifecycle, best-effort protection and native evidence. The experiments support **controlled platform integration**, not immediate customer activation or a claim of flawless browser automation.

The candidate is isolated on `codex/browser-foundation-experiment`, based on staging `918b22d`. No production import, dependency, migration, main/staging branch, historical evidence, remote PR, merge or deployment is changed. The existing API/auth/tenancy, persistent platform repository, worker ownership and historical evidence are not replaced by this lab's SQLite/stdio harness.

This is not a browser driver built from scratch. Playwright MCP owns selectors, control discovery, native actionability and ordinary browser tools. Scry adds the application-specific execution/evidence lifecycle around that established adapter. The [README](README.md) describes implementation ownership and how to repeat the tests.

## What the experiment established

The controlled cases separately prove POST reads, multiple writes after telemetry, GET logout, assets after saves, allowed and denied redirects, input-triggered and deferred autosaves, usable controls beyond the former inventory cap, labels, a real contenteditable and iframe, normal errors without destroying the browser, native dialogs/tabs, screenshots and secret-safe textual output. A separate surface case exercises batch form fill, hover, element drag, coordinate click/drag, pointer down/up, wheel and navigation back. These use public MCP calls; fixture counters and rendered application outcomes are independent oracles, not an adapter saying that its own work passed.

Fault injection covers parent SIGKILL, cancellation while another Run continues, real Chromium renderer SIGKILL, recorder quota and scoped cleanup. A native timeout does not prove that a business change failed. Successful dispatch remains successful if the subsequent observation fails; uncertainty is reported rather than silently retried. Read-only observation timeouts do not imply that an application-changing action was dispatched.

Masking remains deliberately limited and best effort. Passwords/configured access secrets and payment/bank patterns receive localized solid-black masks; ordinary UI remains visible. No DOM replay, screenshot slideshow, whole-page privacy quarantine, raw-frame storage queue or perfect-redaction gate is introduced. Missed masks and brief intervals before overlays settle remain possible. Evidence must be reviewed before sharing.

## Problems found, causes and changes

| Observed problem                                         | Proven cause / selected correction                                                                                                                                                                                                                                                |
| -------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Ordinary app flows blocked or misclassified              | The previous request-based transaction model guessed business meaning from methods/order. Candidate permission is an explicitly approved testing environment; normal application communication is not treated as one intercepted business commit.                                 |
| WebSocket failure with the first candidate proxy         | Chromium uses CONNECT even for plain `ws://`. Native A/B comparison failed with the custom HTTP-only implementation and passed with established proxy-chain. Replaced transport code; exact approved host/port tunnels, no TLS interception.                                      |
| Dialog handling stalled                                  | Mask-refresh JavaScript waits while a native dialog pauses execution. Skip optional refresh during native dialogs; let the upstream dialog tool handle them.                                                                                                                      |
| Active tabs blocked behind mask work                     | An unresolved evaluation on another editor tab was awaited by every browser call. One pending maintenance task per page and a bounded total wait prevent that task from becoming command admission. Closed/crashed page tasks are retired; warnings remain honest.                |
| Crashed tabs looked like generic timeouts                | Actual renderer death was not surfaced separately. Report page crashes durably/publicly; remove crashed masking sessions; allow explicit recovery without repeating uncertain business changes.                                                                                   |
| Diagnostic floods/memory growth during retries           | ERPNext's unavailable external thumbnail caused thousands of repeated denied requests. Replace unbounded per-request denial arrays with bounded distinct-key aggregates and exact count deltas. This does not make the unavailable asset load.                                    |
| Penpot renderer OOM                                      | Two heavy editor tabs exceeded the explicit 1.5 GiB cgroup cap: `oom_kill=2`, peak at the cap. Adequately resourced repeat passed with zero OOM/crashes; final multi-app console peak was 2,042,970,112 bytes with zero OOM kills. No leak-free or unlimited-capacity claim.      |
| Native video included browser chrome/clipped page bottom | A 720-high virtual display and guessed crop did not account for Chromium decoration. Measure window/capture geometry, then verify decoded edge pixels. Current fixed Linux profile captures all page pixels. Historical recordings are unchanged.                                 |
| Rich-editor text appeared absent                         | Accessibility serialization omitted contenteditable values even when native DOM text was correct, with masks on or off. Qualify rendered preview/actual DOM and screenshot evidence instead of asserting an accessibility serialization guarantee that Chromium does not provide. |
| Timeout/restart receipts were confusing                  | Distinguish failed tool from unknown business outcome; known pre-dispatch rejection from uncertain dispatch; read-only wait failure from app-changing timeout. Preserve failing characterizations and requalify recovery.                                                         |

## Limitations and non-passes

- `viewport-1793387707351` failed with Chromium `Page.captureScreenshot: Unable to capture screenshot`. Its cgroup reported zero OOM; the unchanged repeat `viewport-1793387749938` passed. The exact native screenshot failure cause is not established. No retry wrapper or zero-flake claim is added. Ordinary screenshot errors remain recoverable tool failures.
- The first attempted page-freeze fault did not reproduce the intended stall on this Chromium. It is not counted as proof. The subsequent deliberately unresolved CDP evaluation reproduced the await failure deterministically.
- An early packaged trial `trial-1793387291844` was 12/14: its rich-editor accessibility-value assertion and assumption that an inner timeout must be an outer unknown result were wrong. Independent DOM/native-pixel diagnosis and truthful business-outcome semantics—not assertion deletion—explain the corrected tests.
- Upstream text waits can choose an earlier hidden duplicate; a wait is not a universal application-ready signal. Focused snapshots/find and semantic targets were usable. Some exploratory mistakes were ambiguous selectors, an incorrect expected login string or selecting the wrong tab. They are retained as operator errors, not rebranded as adapter defects.
- ERPNext's optional external onboarding thumbnail host was unavailable from the isolated fixture network; direct DNS lookup failed too. The project CRUD path and original UI worked after navigation. External-thumbnail visual completeness is not claimed.
- Approved-origin policy also denied optional external avatar/update hosts in some applications. Those are network-policy effects, not image redaction. A production environment must explicitly configure required asset/API/realtime origins; these trials do not prove unrestricted external-asset visual completeness.
- Original deep journeys started before the final recording geometry correction. Their videos are retained but are not offered as full-viewport fidelity proof. The final packaged-adapter revisits use the corrected geometry and native recordings.
- This qualifies a fixed Linux/Chromium profile and the explicitly exposed tools, not Safari/Firefox/mobile/desktop, uploads/downloads, custom viewport changes, infinite tabs or arbitrary network configurations. The paired upstream Playwright dependency is alpha. No production-stability guarantee is inferred.

## Integration recommendation — next bounded stage

1. Keep the platform's authenticated API, project/environment scope, durable worker ownership and persistent repository. Port the proven action/observation/evidence contract into those existing boundaries; do not ship the lab SQLite/stdio identity as a second platform.
2. Replace the old browser driver/request-commit path for candidate Runs behind an inactive adapter selection. Do not run two actors against one browser. Retain historical evidence readers without rewriting old evidence.
3. Adapt native artifacts/coverage into existing Chronicle custody, authorized retrieval and the dashboard. Browser progress must not depend on recorder/mask admission. Show complete/partial/unavailable recording coverage separately from application outcome and masking warnings.
4. Apply the platform's production container/network isolation, credential store, input/artifact quotas and measured per-Run resource budget. Approved third-party resource origins must be configured explicitly; the lab proxy is not a complete sandbox.
5. Run the same controlled/recovery cases through the real API/queue/worker/evidence path, then independent customer-style agent journeys and live dashboard/player review. Verify review pacing, pause/scrub, evidence access and historical compatibility before any customer activation.

This is a bounded integration proposal, not a demand for another privacy research cycle or a rebuild of unrelated platform features. No activation, merge or deployment is authorized by a passing lab case alone.
